# FGM Report — щоденний звіт менеджера (Streamlit + Bitrix24)

Цей проєкт формує **щоденні звіти менеджерів продажу** на базі даних із Bitrix24 (угоди, історія змін статусів, контакти, джерела, кастомні поля) та показує їх у веб-інтерфейсі Streamlit.

Основна ідея: за обраний день і менеджера порахувати, **які рівні воронки були досягнуті саме завдяки реальним змінам статусу**, з розбивкою за напрямком, країною номера, категоріями та джерелами.

## Що вміє застосунок

- Авторизація менеджера через sidebar (логін/пароль із `st.secrets`).
- Побудова звіту за конкретну дату.
- Два напрямки звітності:
  - **Інстаграм (CRM FGM)**
  - **Сайт (воронка 47)**
- Підрахунок ключових метрик за день:
  - `Взято`, `Дозвон`, `ЦА`, `Зацікавлені`, `Запис`
  - `В дзвінку`, `В повідомленнях`
  - `База`
- Розбивка по країнах номера:
  - `Україна`
  - `Закордон`
- Деталізація по джерелах/категоріях.
- Таблиця з переліком угод і поясненням, як саме угода була врахована.
- Експорт результату в CSV.

## Структура репозиторію

```text
.
├── app_streamlit.py   # Основний Streamlit-додаток
├── report_site.py     # Виділена/дублююча логіка для напрямку “Сайт” (утиліти та builder)
└── requirements.txt   # Python-залежності
```

### Коротко про файли

- **`app_streamlit.py`** — головна точка входу: UI, авторизація, запити до Bitrix24, обчислення метрик, вивід таблиць і CSV.
- **`report_site.py`** — допоміжний модуль із логікою для воронки Site (може бути корисним для рефакторингу/винесення окремого пайплайну).
- **`requirements.txt`** — мінімальний набір бібліотек для запуску.

## Технічний стек

- **Python 3.9+** (через `zoneinfo`, якщо доступний).
- **Streamlit** — UI та state management.
- **Requests** — HTTP-запити до Bitrix24 REST API.
- **Bitrix24 REST API**:
  - `crm.deal.list`
  - `crm.stagehistory.list`
  - `crm.contact.list`
  - `crm.deal.userfield.list`

## Як працює логіка підрахунку

### 1) Відбір угод

1. Беруться угоди призначеного менеджера (`ASSIGNED_BY_ID`) по заданих категоріях.
2. Вибираються ті, що були змінені в обрану дату (`DATE_MODIFY`).

### 2) Історія стадій

Для кожної угоди запитується історія стадій (`crm.stagehistory.list`).
Далі застосунок перевіряє:
- чи була **реальна** зміна стадії в цей день;
- який максимальний рівень був до дня;
- який максимальний рівень став у цей день.

### 3) Рівні воронки

Стадії Bitrix24 мапляться в рівні:
- `1 = Взято`
- `2 = Дозвон`
- `3 = ЦА`
- `4 = Зацікавлені`
- `5 = Запис`

Якщо в день угода піднялась із, наприклад, рівня 2 до 4, у звіті враховуються рівні 3 і 4.

### 4) База (реактивація)

Окремо підтримується логіка “База”: якщо була довга пауза (поріг у днях) і в обрану дату відбулося відновлення руху по стадіях — такі кейси рахуються окремо.

### 5) Регіон і спосіб запису

- За кастомним полем номера визначається група `Україна / Закордон`.
- Для записів на рівні 5 додатково враховується спосіб запису:
  - `Дзвінок`
  - `Повідомлення`

## Налаштування Streamlit Secrets

Застосунок читає конфіг із `st.secrets`.
Локально це зазвичай файл:

```text
.streamlit/secrets.toml
```

### Мінімальний приклад

```toml
WEBHOOK_URL = "https://<your-domain>.bitrix24.ua/rest/<user>/<token>/"
LOCAL_TZ_NAME = "Europe/Kyiv"

[USERS]
  [USERS.manager1]
  name = "Ім'я Менеджера"
  password = "пароль"
  manager_id = 123

  [USERS.manager2]
  name = "Ім'я Менеджера 2"
  password = "пароль2"
  manager_id = 456
```

> Важливо:
> - `WEBHOOK_URL` має закінчуватися `/`.
> - `manager_id` повинен відповідати `ASSIGNED_BY_ID` у Bitrix24.
> - обов’язково зберігайте `secrets.toml` поза git.

## Використання в UI

1. У лівій панелі введіть логін і пароль.
2. Оберіть дату звіту.
3. Оберіть напрямок:
   - **Інстаграм (CRM FGM)**
   - **Сайт (воронка 47)**
4. Натисніть **«Сформувати звіт»**.
5. Перегляньте:
   - загальні KPI за день;
   - таблиці `Україна/Закордон`;
   - деталізацію по угодах.
6. За потреби завантажте CSV.

## Експорт даних

Кнопка **«Завантажити CSV»** формує файл із назвою формату:

```text
report_<manager_name>_<YYYY-MM-DD>_<direction>.csv
```

У CSV входять, зокрема:
- ID угоди
- телефон
- поточний статус
- джерело
- термін
- країна номера
- категорія
- спосіб запису
- результат підрахунку
- причина/коментар

## Типові проблеми та рішення

### 1) `Не задано WEBHOOK_URL у secrets`
Додайте `WEBHOOK_URL` у `secrets.toml`.

### 2) `Не задано USERS у secrets`
Додайте словник `USERS` з логінами/паролями/manager_id.

### 3) Порожній звіт
Перевірте:
- чи в обраний день реально були зміни стадій;
- чи правильний менеджер (`manager_id`);
- чи правильний напрямок (Instagram/Site).

### 4) Повільна генерація
Причина зазвичай у великій кількості угод/історій стадій. У застосунку вже використано кешування довідників (`@st.cache_data`), але повний звіт усе одно потребує серії API-запитів.

## Безпека

- Не комітьте `secrets.toml` у репозиторій.
- Використовуйте окремого технічного користувача Bitrix24 із мінімально необхідними правами.
- Регулярно ротуйте webhook token.

## Ідеї для покращень

- Винести всю бізнес-логіку в окремі модулі та покрити unit-тестами.
- Додати інтеграційні тести з моками Bitrix24 API.
- Додати ролі доступу та хешовані паролі замість plain-text у secrets.
- Додати async/batch оптимізацію запитів.
- Додати періодичні звіти (тиждень/місяць), а не лише за день.
